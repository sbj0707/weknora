# 友邦香港医疗保障助手：Demo 实施蓝图

设计日期：2026-10-20。面向投保客户，覆盖投保前理解产品、持有保单后查询保障、就医及索偿准备。

交付状态：本目录提供设计、提示词、模拟场景种子和验收清单。尚未实现保险 MCP 服务或两个 Skill，也未导入资料、配置运行中的 WeKnora 或完成端到端验收。`scenarios.json` 是拟议服务的数据约定，不是 WeKnora 原生配置导入文件。

## 1. 做到什么程度才算完成

客户可以比较两款医疗计划；系统查到当前模拟客户的保单；结合对应版本的条款解释就医条件；检查索偿附件；交付可下载的繁体中文报告。四项能力必须各有可见证据。

| 能力 | 必须看到的结果 | 完成证据 |
| --- | --- | --- |
| 文档 RAG | 比较或解释保障，同时引用适用产品原文 | 点击引用能定位支持结论的条款、表格或脚注 |
| FAQ | 对标准服务问题返回稳定口径 | FAQ 检索命中记录；快速问答模式验证标准答案 |
| MCP | 现场查询保单、网络、批核或索偿状态 | 工具卡片中的参数和返回值；切换场景后答案变化 |
| Skill | 实际加载技能、执行脚本、生成文件 | 技能读取及脚本调用记录；报告可预览和下载 |

演示使用真实公开产品资料，以及明确标注的模拟客户、医生网络关系、保单和案件状态。产品规则从官方资料获取，业务事实从模拟服务查询。

首版交付两款产品、两个知识库、两个智能体、五个 MCP 工具、两个 Skill、四个可重置场景。客户界面显示“友邦香港医疗保障助手 · 演示原型”，默认繁体中文，金额带币种，引用可点击。

产品：AIA自願醫保尊耀計劃、AIA自願醫保睿選計劃。下列来源于设计日访问，正式演示前应固定下载版本并复核适用范围。

| 编号 | 官方入口 | 需要整理的资料 |
| --- | --- | --- |
| S01 | [睿选产品页](https://www.aia.com.hk/zh-hk/products/health/vhis-select-wise) | 产品简介、保障表、保单契约、标准保费表 |
| S02 | [尊耀产品页](https://www.aia.com.hk/zh-hk/products/health/vhis-privilege-ultra) | 产品简介、保障表、保单契约、标准保费表 |
| S03 | [产品简介目录](https://www.aia.com.hk/zh-hk/help-and-support/product-brochures-individuals) | 核对香港版本、下载资料和产品名称 |
| S04 | [预先批核及出院免找数](https://www.aia.com.hk/zh-hk/health-and-wellness/pre-approval-medical-expense-cashless-service) | 适用产品、申请步骤、所需资料、限制条件 |
| S05 | [医疗索偿指引](https://www.aia.com.hk/zh-hk/help-and-support/health-care-and-claims/how-to-file-a-claim/medical) | 医疗费用与住院现金的区别、索偿文件、AIA+ 步骤 |

下载 PDF 时保存真正的文件地址，避免把 PDF 查看器页面当成条款正文。页面中的产品简介、契约、费率可能分别更新，需要逐项登记。

建议资料量为 8～12 份：两款简介及契约、保障表（若已在简介内无需重复上传）、预先批核说明、索偿指引、相关申请表。正式费率演示可后置，先完成条款解释和服务闭环。

每份资料登记：`document_id`、产品全名、内部演示产品代码、香港地区、语言、币种/适用计划、资料类型、文件标示版本、原始 URL、获取时间、内容哈希。文档未标示版本时记录“未标示”，不要用下载日替代生效日。

两个内部产品代码可定义为 `DEMO-HK-SELECTWISE` 和 `DEMO-HK-PRIVILEGE-ULTRA`，均不是友邦官方产品代码。将模拟保单中的 `contract_document_id` 绑定到实际入库的契约文档；完成绑定后才开启个人保障解释演示。

资料优先级：匹配保单的契约及特别条款 → 对应版本保障表 → 产品简介；服务操作使用适用服务指引。存在冲突或版本不明时指出差异并请求确认。

## 3. 用两个知识库组织内容

### 文档知识库：AIA-HK-医疗产品与服务

按产品/版本和客户服务分文件夹，标题包含产品全名、香港、资料类型和版本。服务文件如通用于多个产品，在文件说明中写明范围。

解析后人工检查六类内容：产品名、币种、计划选项、表格列名、脚注、限制条件。分块从保留完整条款和表格上下文开始调试，避免将“保障内容”和“条件限制”拆成彼此不可理解的片段。用混合检索和重排序，再通过阅读原文补全上下文；参数通过验收题调整。

需要特别验证的官方事实：睿选计划在香港的半私家房资格涉及指定医院、所有相关主诊注册医生及外科医生的网络资格，以及医疗服务前的预先核准。具体表述以入库版本为准。[来源 S01](https://www.aia.com.hk/zh-hk/products/health/vhis-select-wise)

### FAQ 知识库：AIA-HK-客户服务 FAQ

先写 12 条并调通，再扩展到 40 条。分类建议：术语 8 条、产品理解 8 条、就医与预先批核 8 条、索偿及 AIA+ 操作 16 条。

每条维护标准问、3～5 个相似问、容易误匹配的反例问、一个经核对的答案。使用当前页面下载的导入模板；多值字段分隔方式为 `##`。官方来源及更新时间写在答案末尾或单独维护的资料登记中，不假定导入器支持任意自定义字段。

首批问题：

1. 每年自付费是什么意思？
2. 自付费和保费有什么区别？
3. 不设分项赔偿限额是否等于所有费用均可获赔？
4. 产品简介和保单契约有什么区别？
5. 医疗费用预先批核是什么？
6. 出院免找数服务如何申请？
7. 医院在网络内，是否就满足所有病房保障条件？
8. 医疗费用索偿通常需要哪些文件？
9. 住院现金与医疗费用索偿的文件要求是否相同？
10. 如何通过 AIA+ 提交医疗索偿？
11. 如何查看索偿结果？
12. 官方要求补件时，下一步如何办理？

“我已获批吗”“我的自付费是多少”属于个人动态事实，不能由通用 FAQ 代答。保险术语答案需要保留产品适用条件，避免把某产品规则写成所有保单通用规则。

FAQ 反例主要按完全匹配排除，需额外测试否定、改写和带个人信息的问题。快速问答可配置 FAQ 优先及直接回答阈值；智能推理中的检索行为单独验证，不能假定同样会直接返回标准答案。

## 4. 模拟客户与四个可切换场景

人物为虚构客户“陳家明”，持有模拟睿选保单，保单货币 HKD、每年自付费 HKD 18,000。该金额是为演示选取的计划选项，不代表真实客户保单。客户及场景见 `scenarios.json`。

| 场景 | 业务事实 | 预期行为 |
| --- | --- | --- |
| A：就医前待批核 | 指定医院、相关医生网络资格已核实；批核 pending | 说明尚未确认全部条件，列出批核待办 |
| B：就医前已批核 | 与 A 同一模拟就医事件；批核 approved，记录适用项目和期限 | 列明已核实条件及批核范围，保留契约其他限制 |
| C：既往就医待补件 | 独立的既往就医事件；缺申请书第二部分和诊断证明 | 给出两项待补文件及来源，不混用 A/B 事件 |
| D：客户已补一份附件 | 后台仍为 C；当前会话新增申请书第二部分 | 本地准备清单只余诊断证明；后台仍显示两项待补 |

场景由维护人员通过本地 fixture/启动参数切换，控制接口不暴露给客户智能体。A/B 切换后使用新会话或要求重新查询。D 是会话附件变化，不等于已向保险公司提交，也不自动改变后台状态。

医院可采用官方名单快照，例如仁安醫院，但要保留快照的原始更新时间和获取时间。医生 ID、就医安排、网络关系和批准记录均为模拟。过期、无时间或不匹配产品版本的网络数据返回待核实。

## 5. MCP 服务设计

在 `examples/` 下新增独立的 `aia-hk-demo/` 服务，参考 [现有 MCP Demo](../../../examples/mcp-demo/README.md) 的服务、Bearer 鉴权和启动方式；不要把现有通用演示数据直接改成保险数据。

第一版采用 JSON fixture、Streamable HTTP、Bearer 鉴权、五个只读工具。用户身份由演示服务的令牌或服务端配置固定到 `DEMO-CUSTOMER-001`，客户不能通过工具参数任意切换身份。

| 工具 | 参数 | 关键返回值 |
| --- | --- | --- |
| `get_my_policies` | 无 | 当前演示客户的保单列表、产品、状态、币种、契约文档绑定 |
| `get_policy_benefits` | `policy_id` | 已选计划、自付费、特别条款核对状态、契约文档 ID |
| `search_provider_network` | `policy_id, hospital_name, doctor_ids, service_date` | 医院资格、每位医生网络状态、核实范围、来源及快照时间 |
| `get_preapproval_status` | `policy_id, encounter_id` | pending/approved 等状态、批准项目、时间、病房及限制 |
| `get_claim_status` | `policy_id, claim_id` | 状态、已收文件、待补文件、更新时间 |

所有工具在后端校验资源归属，越权保单返回 `access_denied`，不存在的对象返回 `not_found`；依赖不可用返回 `temporarily_unavailable`。无法确认的字段用 `unknown`/`null`，不能转成 false 或否定结论。

通用结果信封建议为：

```json
{
  "ok": true,
  "simulated": true,
  "source_kind": "mock_business_system",
  "scenario_id": "A",
  "queried_at": "运行时产生的带时区时间",
  "data_updated_at": "fixture 业务记录的更新时间",
  "data": {}
}
```

网络快照额外返回 `source_url`、`source_published_at`、`retrieved_at`、`validity_verified`。`queried_at` 只能说明何时查询，不能代表底层数据刚刚更新。内部 fixture 提示不得作为产品规则。

部署连接：后端本机运行时使用本机服务地址；WeKnora 后端在 Docker 中时采用容器可达的服务名或宿主机地址。容器内 `127.0.0.1` 指向容器自己。需要从 WeKnora 后端实际验证 TCP、鉴权和工具发现，必要时在系统配置中放行精确的演示服务主机；不能仅凭浏览器能打开就判定连通。

## 6. 两个 Skill 的实施规格

Skill 说明、脚本和报告模板独立打包。Agent 查询知识库和 MCP，再把已核对的结构化数据传给脚本；脚本不需要另存保险业务令牌。以下是待实现的目录规格，不表示本目录已提供可安装包。

```text
medical-plan-comparison/
  SKILL.md
  scripts/render_report.py
  templates/comparison.html
medical-claim-preparation/
  SKILL.md
  scripts/check_materials.py
  scripts/render_report.py
  templates/claim-checklist.html
```

### 产品比较 Skill

触发：客户要求结合自身关注点比较两款计划并交付文件。

输入：预算是否明确、常用就医地区、病房偏好、公司医疗是否存在及已知信息、两款产品的已检索事实和来源。缺少个人偏好可以追问；缺少产品证据时相应单元格写“待确认”。

步骤：检索两款匹配版本资料 → 阅读表格和限制 → 填充对照数据 → 检查每项结论来源 → 脚本生成 HTML 和 JSON。

输出：`medical-plan-comparison.html`、`medical-plan-comparison.json`。报告包括需求摘要、地域/病房/自付费/服务条件对照、资料版本、待向顾问确认的问题、引用链接。按客户关注点说明差异，不凭少量问答断言某产品最适合客户。

首版不演示报价和赔款测算；后续加入时使用核对过的结构化费率/规则及脚本计算，并明确前提与版本。

### 索偿准备 Skill

触发：客户要求根据保单、案件和已上传文件检查材料并生成清单。

步骤：查询保单及案件 → 检索对应索偿类别的文件要求 → 逐份读附件 → 生成证据清单 → 脚本检查 → 渲染 HTML 和 JSON。

输入材料记录至少包含：文件名、类型、可读性、姓名/日期/事件是否匹配、是否已交后台、证据页码或段落、核对状态。一个附件可能同时包含多类证明；扫描件不能读取时标记 `needs_review`，不直接认定缺件。

输出：`medical-claim-checklist.html`、`medical-claim-checklist.json`。内容包括保单及事件摘要、后台状态、本轮附件、已备材料、待补材料、待核实项、官方办理入口、逐项来源。后台缺件和本地已备但未提交分别展示。

允许状态：`present`（已读并匹配）、`missing`（已核对未提供）、`needs_review`（无法判断）、`not_applicable`（有依据地不适用）。每项记录原因，避免用有/无文件名替代实质检查。

两类 HTML 使用 UTF-8、完整页面结构及转义后的客户输入，引用用可点击来源链接。JSON 保留文档 ID、页码/条款、URL、核对时间，方便人工复核；对话里的临时引用句柄不能作为导出报告唯一来源。

远程沙箱产物写入 `/workspace/output`。先使用 Docker/E2B/Cube 中一种已验证的后端；macOS Lite 本机模式文件保存在本机项目，交付入口不同，应单独验证。第一版采用 HTML/JSON，Word/PDF 属于后续展示增强。

## 7. WeKnora 按这个顺序配置

| 步骤 | 操作 | 通过条件 |
| --- | --- | --- |
| 1 | 确认可运行 WeKnora；配置对话、Embedding、Rerank 模型；准备一个沙箱 | 文档检索及沙箱生成一个文件分别成功 |
| 2 | 下载、登记并入库两款资料和服务指引 | 用六个核心问题人工检查原文引用 |
| 3 | 建 FAQ 库，导入首批 12 条 | 检查实际导入状态、相似问及否定问命中 |
| 4 | 实现、启动模拟 MCP，选择场景 A | 从后端可达，带正确鉴权发现五个工具 |
| 5 | 工具箱 → MCP服务：连接、同步工具、填写用途说明 | 对话能查询模拟保单，并正确报告缺失/错误状态 |
| 6 | 设置 → 沙箱配置：验证后端；工具箱 → 技能管理：上传两个技能包并安装 | 状态就绪，依赖安装成功，脚本产物可下载 |
| 7 | 建快速问答及智能推理两个 Agent，使用 `agent-prompts.md` | 每项能力都在合适模式下可见 |
| 8 | 绑定契约版本、复核场景、跑验收题及演示彩排 | 达到第 10 节全部硬性标准 |

快速问答 Agent 名称“香港保险咨询”：只绑定两个知识库，启用引用，配置 FAQ 优先；关闭 MCP、技能和联网搜索。用其验证 FAQ 及单文档问答。

智能推理 Agent 名称“香港保障与索偿助手”：指定两个知识库、五个保险 MCP 工具、两个已就绪技能和沙箱；启用引用、文件处理和所需读取/执行工具。首版关闭联网搜索与长期记忆，使演示资料范围和场景容易复现。

两者共享经核对的事实原则，智能推理增加工具使用规则。根据实际模型支持选择参数，先把迭代预算设为能完成“查询 → 检索 → 阅读 → 运行脚本 → 回答”的范围（例如 15～20 轮），再通过彩排观察实际用量和时延。

首版直接使用 WeKnora 网页对话和产物面板。需要面向客户的独立页面时，再使用现有嵌入能力；此阶段保留后端调用记录供验收，客户文案聚焦保障解释与下一步行动。

## 8. 八分钟现场脚本

| 时间预算 | 模式/场景 | 客户原话 | 展示证据 |
| --- | --- | --- | --- |
| 1 分钟 | 快速问答 | 「每年自付費同保費有咩分別？」 | 标准 FAQ 与来源 |
| 1.5 分钟 | 智能推理，新客户会话 | 「我有公司醫療，想比較尊耀同睿選，重點睇醫院同病房限制，幫我出比較表。」 | 两款引用、comparison Skill 和下载文件 |
| 1 分钟 | 智能推理，模拟持单客户 | 「查一下我的保單、自付費及適用條款。」 | MCP 保单及版本绑定 |
| 1.5 分钟 | 场景 A | 「我打算入住仁安醫院半私家房，現時需要先確認甚麼？」 | 网络查询＋pending 批核＋条款条件 |
| 1 分钟 | 场景 B，重新查询或新会话 | 「請重新查詢預先批核結果，再更新就醫準備事項。」 | MCP 状态变化、批准范围 |
| 1 分钟 | 场景 C，新会话 | 「幫我查 DEMO-CLAIM-001，核對這些附件並生成索償準備清單。」 | 两项待补及 claim Skill 文件 |
| 1 分钟 | 场景 D，同一 C 会话补附件 | 「我補上了申請書第二部分，請更新清單。」 | 本地只余一项；后台状态仍未变 |

比较与索偿生成文件需在目标环境提前计时；八分钟是演示预算，不是系统性能承诺。长任务现场可展示一份真实生成的备份产物，同时如实说明当前任务仍在执行。

## 10. 放行标准与实施排期

硬性标准：所有个人事实与模拟工具结果一致；关键产品规则和结论有匹配来源；没有把待批核说成获批；没有跨市场或产品版本混用；材料不可读/身份不符能被识别；越权被后端拒绝；两个 Skill 均实际运行并交付可打开文件；四个场景可重置。任一失败先修复再演示。

整体目标：30 题至少 27 题通过，且硬性标准对应题全部通过；现场主流程连续三次通过。时延目标由目标环境彩排决定并登记，不把检索分数视为业务正确率。

| 阶段 | 参考工作量，环境及资料已可用时 | 交付物 |
| --- | --- | --- |
| 第 1 阶段 | 1 天 | 官方资料登记、两库、12 条 FAQ、六题引用检查 |
| 第 2 阶段 | 1 天 | 模拟 MCP 五工具、四场景、归属和异常处理 |
| 第 3 阶段 | 1～2 天 | 两个 Skill、HTML/JSON 模板、沙箱交付 |
| 第 4 阶段 | 1 天 | FAQ 扩至 40 条、30 题验收、三轮彩排 |

环境、模型和资料可用性会影响上述估算。实施先后依赖为：基础运行 → 资料及引用 → 模拟 MCP → Skill → 验收 → 客户页面增强。

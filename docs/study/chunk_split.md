在当前 WeKnora 项目里，界面提供 **4 个选项：自动、按标题切分、结构感知、按长度切分**。其中，**“自动”负责选择策略，实际执行分块的算法有 3 种**。

| 界面选项 | 配置值 | 核心做法 | 适用文档 |
|---|---|---|---|
| 自动 | `auto` | 分析每份文档的结构，选择下面三种算法，并在结果不合格时回退 | 文档类型混杂的知识库 |
| 按标题切分 | `heading` | 以 Markdown 标题层级划分章节，长章节再细切 | 技术文档、操作手册 |
| 结构感知 | `heuristic` | 根据章节编号、分页符等线索寻找边界 | PDF 解析文本、OCR 文本、纯文本书籍 |
| 按长度切分 | `legacy` | 按字符预算和分隔符递归切分 | 结构不明显的普通文本 |

**1. 按标题切分：优先保留章节结构**

例如：

```markdown
# 安装指南
## 环境要求
……
## 安装步骤
……
## 常见问题
……
```

分块器会根据标题分布确定主要切分层级，在章节边界切开：

- 一个章节比较短，可以整体成为一个 chunk。
- 一个章节太长，再在章节内部按长度递归切分。
- 相邻小块在满足条件时会合并，避免过度零碎。

每块还会记录所属标题路径，例如 `安装指南 → 安装步骤`，构建向量索引时带上这段上下文，让正文中的“执行以下命令”具有更明确的语境。

这里识别的是**解析后文本中的 Markdown 标题**。原始 PDF 里字号较大的文字，需要解析器先将它转换成标题，才能按此规则识别。

**2. 结构感知：通过格式线索判断边界**

有些文本没有 `#`、`##`，但仍存在章节结构，例如：

```text
第一章 总则
……

1.1 适用范围
……

第二章 施工要求
……
```

它通过规则识别：

- 分页符；
- `1.2.3` 等编号小节；
- `第一章`、`Chapter 3`、`Kapitel 2` 等章节标记；
- 全大写短标题；
- 分隔线、页脚和连续空行。

识别后，结合块大小把内容组织成 chunk；过长的区段仍会进一步递归切分。

它适合标题格式不规范但保留结构线索的文本。**如果 OCR 把章节编号和换行也识别错了，分块效果仍会受影响。**

**3. 按长度切分：按分隔符逐步细切**

它以 `chunk_size` 为目标预算，按分隔符优先级递归切分。项目默认顺序是：

```text
段落（双换行） → 单换行 → 中文句号
```

可以理解为：先尝试按段落切；段落太长，再按行切；行仍太长，再按句号切，最后把小片段合并成接近目标大小的块。

它也会处理重叠，并保护代码、公式、表格等内容，所以**不是机械地每隔 512 个字符切一刀**。块大小也不保证完全一致。

接口还支持 `recursive`，它是 `legacy` 的别名，两者执行同一种算法。

**4. 自动：文档画像 → 选择候选策略 → 校验 → 回退**

当前实现通过本地统计规则分析文档，**分块策略选择本身不调用大模型**。

具体选择条件是：

| 文档特征 | 自动模式的选择 |
|---|---|
| Markdown 标题至少 3 个，且标题行占比大于 0.5% | 将“按标题切分”加入候选链 |
| 结构标记至少 5 个，或存在分页符，或存在中／英／德章节标记 | 将“结构感知”加入候选链 |
| 所有文档 | 最后加入“按长度切分”作为兜底 |

因此，不同文档可能得到不同的尝试链：

```text
标题结构和其他结构线索都明显：
按标题切分 → 结构感知 → 按长度切分

只有其他结构线索明显：
结构感知 → 按长度切分

没有明显结构：
按长度切分
```

**箭头表示前一个结果不合格时，才尝试下一个。** 系统会检查是否产生过多小块、是否有明显超大的块、长文档是否只切出一块等，通过检查就采用结果。

所以，“自动”的含义是**按预设规则为每份文档选择合适的算法**；它不会自动比较检索准确率，也不会自动调优所有分块参数。选择规则见 [profiler.go](/Users/barryshen/source_code/WeKnora/internal/infrastructure/chunker/profiler.go:216)，回退逻辑见 [strategy.go](/Users/barryshen/source_code/WeKnora/internal/infrastructure/chunker/strategy.go:273)。

另外，**父子分块是可叠加的两级组织方式**：先切较大的父块，再切较小的子块；用子块做精确检索，命中后取父块补充上下文。它可以与上述策略结合使用。

还要留意：当前代码中，**策略留空会使用 `legacy`，不等于 `auto`**。修改策略后，已有文档需要重新解析才会按新策略分块。



**PPT 通常适合“以幻灯片页为基础，再按内容多少细分”**，因为一页往往围绕一个主题展开。

| 页面情况 | 合适的切法 | 原因 |
|---|---|---|
| 普通内容页：标题＋几个要点 | 一页一个 chunk | 保留完整主题 |
| 内容密集页：多个段落、多个主题 | 一页拆成多个 chunk，每块带上页标题 | 提高检索精度 |
| 封面、目录、过渡页 | 单独标记，或降低检索权重 | 单独检索价值通常较低 |
| 连续几页讲同一主题 | 每页独立检索，命中后补充相邻页或章节上下文 | 同时兼顾精度和完整性 |
| 图表、流程图为主 | 将图片识别结果、图表说明与所在页关联 | 仅提取文字会丢失图中的关系 |

例如，第 8 页讲“系统部署”，内容很多，可以切成：

```text
第 8 页：系统部署
├── chunk 1：环境要求，附“系统部署”标题
├── chunk 2：部署步骤，附“系统部署”标题
└── chunk 3：注意事项，附“系统部署”标题
```

**当前 WeKnora 的实现，是先把 PPT 解析成 Markdown，再执行前面介绍的通用分块策略。** 项目的 MarkItDown 解析路径见 [markitdown_parser.py](/Users/barryshen/source_code/WeKnora/docreader/parser/markitdown_parser.py:39)。

MarkItDown 上游实现会逐页提取内容，添加幻灯片编号标记，并把识别到的页面标题转换为 Markdown 标题。因此，解析结果可能类似：

```markdown
<!-- Slide number: 8 -->
# 系统部署
环境要求……
部署步骤……

<!-- Slide number: 9 -->
# 故障排查
……
```

这一行为可见 [MarkItDown 的 PPTX 转换源码](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/converters/_pptx_converter.py)，具体输出取决于所用版本和解析引擎。

接下来，不同策略的效果是：

- **按标题切分**：通常接近按有标题的幻灯片划分；内容过长再细切，小块可能合并。
- **自动**：根据解析出来的标题和结构信号选择算法。标题足够明显时会优先尝试标题分块。
- **结构感知**：利用解析文本中的章节编号、分页符等线索；能否接近按页切，取决于解析器保留了什么。
- **按长度切分**：主要看长度和分隔符，可能把一页拆开，也可能把相邻页放进同一个 chunk。

所以，**当前项目中的“自动”不保证一页一个 chunk，页码定位信息也不等于强制按页分块。** 如果你的目标是严格保留 PPT 页边界，需要专门按幻灯片边界切分；如果目标是知识问答，可以先用自动模式，并检查预览是否把不同页的主题混在一起。

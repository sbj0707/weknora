# 文档页面图片辅助回答：设计与任务清单

> 设计日期：2026-10-20。本文记录待实现方案，不代表功能已经完成。

## 1. 目标与范围

当知识库开启「使用页面图片辅助回答」时，根据最终检索命中的 Chunk 查找其原文页面已保存的图片，将文字证据与页面图片一起传给回答模型，使模型能够结合图表、单位、脚注和版面内容生成答案。

这里的页面图片指原文的**整页截图**。现有 `chunk_images` 是从 `chunks.image_info` 投影得到的图片查询表，不能直接视为完整页面截图表。

### 已确认的需求

- 在知识库设置的「图像处理」页签、「图片属性观察」上方增加两个参数。
- 参数一：是否使用页面图片作为生成答案的依据。
- 参数二：仅在参数一开启时显示，控制文档解析、分块过程中是否自动保存页面图片。
- 参数一开启时，Chunk 编辑/详情界面提供手动保存关联页面图片的操作；不要求同时开启参数二。
- 回答时读取已保存的对应页图片，以真实图片输入参与模型调用。

### 建议实施边界

- 首期支持 PDF；PPT 后续按幻灯片扩展。
- Word、Excel 需要先确定转换、分页及原文定位对应规则，不将段落号或行号直接当成页码。
- 复用现有检索、重排、Chunk 定位、存储引擎和模型协议适配能力。
- 普通知识库问答和 Agent 检索工具两条回答路径均需接入。
- 默认关闭新功能，已有知识库、OCR、图片描述和图片属性观察行为保持兼容。

## 2. 知识库配置

扩展现有 `image_processing_config` JSON 配置，不将页面图片输入与已有图片属性观察、OCR 或图片描述开关绑定。

| 页面字段 | 建议字段名 | 默认值 | 行为 |
| --- | --- | --- | --- |
| 使用页面图片辅助回答 | `use_page_images_for_answer` | `false` | 控制该知识库的页图是否参与答案生成 |
| 文档处理时自动保存页面图片 | `auto_save_page_images` | `false` | 仅在上一项开启时显示，在文档处理期间生成页图 |

示例为原配置的新增字段，保存时需保留其他现有字段：

```json
{
  "use_page_images_for_answer": true,
  "auto_save_page_images": true
}
```

- 两项均关闭：保持原有文本回答流程。
- 仅第一项开启：使用已有或手动保存的页图，不自动生成页图。
- 两项均开启：新上传、重新处理文档时自动生成页图，回答时可以使用。
- 第一项关闭时，第二项不生效；已有图片保留，但不再发送给回答模型。
- 旧配置缺少新字段时按 `false` 处理。
- 保存配置不自动触发历史文档批量解析或图片生成；历史文档通过单独的补建操作处理。
- 配置读取、更新、导入导出、知识库复制时同步适配新字段，避免整体替换 JSON 时丢失原有配置。

## 3. 页面图片存储与关联

### 3.1 页面图片资产

建议新增 `document_page_images` 表，图片文件通过当前知识库使用的存储引擎保存，数据库只存元数据，不保存 Base64 图片正文。

| 字段 | 用途 |
| --- | --- |
| `id` | 资产记录 ID |
| `tenant_id`、`knowledge_base_id`、`knowledge_id` | 租户、知识库和文档归属 |
| `source_hash` | 绑定原文件版本，复用文档文件哈希语义 |
| `page_number` | 原文页码，从 1 开始 |
| `storage_key` | 图片在现有存储引擎中的定位信息 |
| `mime_type`、`width`、`height`、`size` | 图片格式、尺寸和字节数 |
| `render_profile` | 渲染规格标识，区分分辨率、压缩等设置 |
| `status`、`error_message` | 等待、生成中、成功、失败及失败原因 |
| `created_at`、`updated_at` | 创建和更新时间 |

唯一约束覆盖「租户、文档、原文件版本、页码、渲染规格」。同页多个 Chunk 共享一张页图，不逐 Chunk 复制图片。

### 3.2 与 Chunk 的关系

- 自动关联使用现有 `chunks.source_locators`，提取对应文件版本的有效 PDF 页码。
- 一个 Chunk 可以关联多个页面；多个 Chunk 可以关联同一页面。
- 不通过 Chunk 编号、字符偏移或相似度猜测原文页码。
- 手工确认的 Chunk—页面关系单独记录，并标明「手工关联」，不写成自动验证的 `mapping=exact`。
- 手工关系也绑定文档、文件版本和 Chunk 内容修订；正文再次修改后需重新确认关联。
- 页面生成任务是幂等任务；并发处理同一页时避免重复渲染和重复写入。

### 3.3 生命周期

- 原文件更新后，旧版本页图不参与新版本的回答。
- 文档删除、知识库删除时清理对应资产和文件，兼容项目现有引用与清理约定。
- 文档复制、移动时处理存储归属和对象引用，避免沿用错误的知识库或租户路径。
- 关闭开关不删除已有资产；重新开启时可复用仍然有效的页图。

## 4. 自动保存与历史文档补建

```text
文档解析、分块
  → 检查知识库的两个开关
  → 提交后台页面渲染任务
  → 按文档逐页生成整页图片
  → 保存至当前存储引擎
  → 更新资产状态
```

- 每页独立记录状态，支持查询进度、失败重试和重新生成。
- 已存在同文件版本、同页码、同渲染规格的成功资产时直接复用。
- 图片生成失败不导致已成功的文本分块和索引全部失败。
- 在文档界面提供「补建页面图片」入口，无需重新提取正文、分块或建立文本索引。
- 渲染任务执行期间再次校验文件版本，防止旧任务覆盖新版本资产。
- 任务提交和执行端均校验权限及知识库配置，不能仅依赖前端显示控制。

## 5. Chunk 手动保存页面图片

在第一个开关开启时，于 Chunk 编辑/详情界面增加「保存关联页面图片」操作。

| Chunk 情况 | 操作行为 |
| --- | --- |
| 有有效原文页码 | 展示对应页码，提交这些页面的图片生成任务 |
| 对应页图已经保存 | 展示图片状态和预览，支持重新生成 |
| 没有页码 | 从原文预览选择页面，经用户确认后建立手工关系 |
| 正文修改导致定位失效 | 不复用旧精确定位；要求重新确认页面 |
| 当前文件格式暂不支持 | 明确提示，不生成虚构页码或空资产 |

现有 `internal/application/service/chunk.go` 在正文变化时会清除 `SourceLocators`，该保护需要保留。手动关系不得绕过文件版本或正文修订校验。

保存正文与保存页图分开触发，避免每次编辑正文都重新截图。点击保存页图时必须明确使用的是当前已保存的 Chunk 修订，防止尚未保存的编辑内容与旧关联混用。

## 6. 答案生成链路

### 6.1 收集图片证据

在检索、重排、上下文合并及最终筛选完成后，模型调用前增加图片证据收集步骤：

```text
最终采用的 Chunk
  → 分别检查所属知识库开关
  → 读取 source_locators 或有效手工关联
  → 查找当前文件版本已成功保存的页图
  → 按文档、文件版本、页码去重
  → 应用图片数量、尺寸和输入预算
  → 将文字证据、来源说明和图片交给回答模型
```

- 使用最终实际进入上下文的来源，避免发送已被重排淘汰或预算裁剪的 Chunk 所在页面。
- 父子 Chunk 合并、上下文扩展后保留原始来源关系，防止携带与实际引用不对应的页图。
- 跨知识库检索逐库判断设置，关闭功能的知识库不贡献页图。
- 多个命中指向同一页时只发送一张；跨页 Chunk 可以贡献多张。
- 无可靠页码、页图缺失、任务未完成、文件版本不匹配或读取失败时，记录跳过原因并继续文本回答。
- 回答期间只读取已保存资产，不临时渲染整份文档。

### 6.2 模型输入与引用

- 复用现有 `Images` / `MultiContent` 协议适配能力，发送真实图片内容。
- 后端通过当前存储引擎读取页图，转换为所选协议支持的图片输入；不只在提示词中放置需要登录的前端地址。
- 每张图附带文档 ID、文档名称、页码及关联 Chunk 标识，维持图片与文字证据的对应关系。
- 将页图标记为来源证据，其中出现的文字不作为新的用户指令。
- 根据项目现有引用协议返回文档和 Chunk 引用，保留对应页图的来源信息供追溯。
- 只对实际发送的图片记录「已使用图片证据」，不能将仅保存或被预算淘汰的图片标记为模型已查看。
- 检查最终回答模型是否支持视觉，而不是检查知识库的图片描述模型。
- 非视觉模型给出明确提示并继续文本回答；不自动替换所选模型，不声称模型看过图片。
- 用户上传图片与知识库页图分别记录来源，统一纳入输入预算，保留原有用户图片处理能力。
- 按相关性优先选择页面，限制单次图片数量、单图尺寸、总字节数和模型输入预算；具体阈值实施时集中配置。

### 6.3 两条回答路径

- 普通知识库问答：在最终上下文转模型消息的过程收集并附加图片。
- Agent 问答：检索工具返回图片证据与来源，复用工具图片输入机制；多轮工具调用共享图片预算并去重。
- 两条路径复用统一的资产查询、权限校验、版本校验和预算逻辑。
- 持久化来源及图片使用摘要，不将大段 Base64 正文写入业务记录或日志。

## 7. 渲染技术与部署影响

现有 DocReader 的 `docreader/parser/pdf_parser.py` 已使用 `pypdfium2`，具备整页渲染基础，但现有 gRPC 接口主要为解析服务，没有独立的按页渲染接口。

建议复用该渲染实现并提供按页渲染能力，保持页面图片保存与现有 OCR、图片描述任务独立，避免为了截图而强制将原生 PDF 当扫描件重新解析。

| 实现方式 | 部署影响 |
| --- | --- |
| 扩展 DocReader 按页渲染接口 | 需同步更新 app、frontend 和 DocReader 镜像，复用现有 PDF 渲染依赖 |
| 将渲染能力放入 app 镜像 | 可以只更新 app/frontend，但需在 app 镜像加入渲染依赖并维护调用及资源限制 |

实施前需明确使用哪一种方式，不能承诺扩展 DocReader 后仅更新 app/frontend 即可。数据库通过新增迁移建立资产及关联存储，**不修改已经执行的 111–115 脚本**；按项目当前支持范围同步考虑 PostgreSQL、SQLite。

- [ ] 在「图片属性观察」上方添加两个开关，复用现有设置布局和国际化机制。
- [ ] 配置保存、重新加载、导入导出及复制保留新字段与原有字段。
- [ ] 为 Chunk 编辑/详情增加手动保存、状态、预览和重新生成入口。
- [ ] 增加无定位时的原文页面选择与手工关联确认流程。
- [ ] 增加历史文档补建入口及任务进度展示。
- [ ] 在非视觉模型、图片不可用等场景给出清晰反馈。

### 资产与后台任务

- [ ] 确定页面渲染部署方式及首期支持格式。
- [ ] 定义页图资产和手工关联实体，新增数据库迁移及索引。
- [ ] 实现资产 Repository、Service、存储读写及权限校验。
- [ ] 实现页面渲染、图片压缩、任务状态、幂等去重、失败重试和版本校验。
- [ ] 接入文档处理的自动保存及历史文档补建流程。
- [ ] 实现 Chunk 手动生成和手工关联接口，校验文件归属及正文修订。
- [ ] 接入文档、知识库删除及文档复制、移动的资产生命周期。

### 回答链路

- [ ] 建立统一的图片证据收集器，处理来源关系、文件版本、权限、去重和预算。
- [ ] 接入普通知识库问答，保证图片与最终上下文来源一致。
- [ ] 接入 Agent 检索工具和多轮模型调用。
- [ ] 通过实际多模态消息发送图片，保留用户上传图片能力。
- [ ] 处理非视觉模型及图片读取失败等降级情况。
- [ ] 记录实际发送的页图、关联 Chunk、数量、字节数和跳过原因，不记录 Base64 图片正文。

## 9. 验收清单

- [ ] 两个开关默认关闭，旧知识库和现有图片处理行为不变。
- [ ] 第一项开启、第二项关闭时，可以使用手工生成的页图回答。
- [ ] 自动保存可生成 PDF 各页图片，多 Chunk 共用同页资产。
- [ ] 同一文件、版本、页码及规格的并发任务不会重复创建资产。
- [ ] 历史文档可以单独补建页图，无需重建原有文本索引。
- [ ] 跨页 Chunk、同页多 Chunk、父子合并及上下文裁剪后的图片来源正确。
- [ ] 多知识库检索遵循各自开关，不能跨租户读取或生成页图。
- [ ] 无页码和已编辑 Chunk 不能错误复用旧定位，手工页面关系可追溯。
- [ ] 文件更新后不使用旧页图，过期任务不能覆盖新版本资产。
- [ ] 检查实际发给模型的请求，确认包含可读取的图片内容及正确来源说明。
- [ ] 普通问答与 Agent 路径均可结合页面图表回答，引用仍能回到对应文档和页面。
- [ ] 非视觉模型明确反馈；无图、生成失败及预算超限时仍能完成文本回答。
- [ ] 用户上传图片与页图可同时参与回答，预算和来源互不混淆。
- [ ] 文档删除、复制和移动后的资产引用与存储归属正确。
- [ ] 执行受影响的后端测试、前端类型检查及构建，并完成渲染依赖所在镜像的构建验证。

## 10. 建议实施顺序

1. 确定渲染部署方式，落实 PDF 渲染及存储契约。
2. 数据实体、数据库迁移、资产服务、后台任务及核心测试。
3. 知识库配置、Chunk 手动生成与手工页面关联。
4. 文档自动生成及历史文档补建。
5. 普通知识库问答的图片证据输入。
6. Agent 工具图片证据接入、预算及来源追溯。
7. 生命周期、失败降级、兼容验证和端到端验收。

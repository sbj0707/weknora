# Native knowledge-base move-target discovery

`GET /api/v1/knowledge-bases/{id}/move-targets` now runs natively. API-key retrieve/full-access policy runs before the Viewer and source-KB read checks. The handler then re-reads the source and requires its owner to equal the original caller tenant; an organization share alone does not permit discovery. This preserves Go's handler check after shared read middleware.

Candidates are live, non-temporary knowledge bases of the same tenant, type and embedding model, excluding the source. Go does not filter candidates by storage provider, storage backend, vector store, creator or the API key's candidate allow-list, so Java does not add these filters. The subsequent move endpoint still applies its own authorization and compatibility rules. Discovery returns the service DTO with credentials redacted, capabilities and best-effort document/FAQ/processing counts. It does not add creator names, share counts or vector-store display metadata from the normal list handler.

Personal pins are scoped to the original tenant/user and sorted by pin status, pin timestamp, then creation timestamp, retaining stable ties. Timestamp comparison preserves nanoseconds on SQLite and the PostgreSQL column precision. Missing count or pin tables do not prevent a readable list; missing users/vector-store tables do not affect this service response.

The actual Go SQLite corpus includes TEXT and BLOB configuration values. Several Go configuration Scanners accept bytes only and ignore TEXT; Java's database decoder preserves that distinction for this route. SQL NULL indexing values remain zero until Go-equivalent defaults run, including FAQ's early return. The legacy storage-provider fallback from request JSON is not applied to database rows. Existing general KB read/write decoders are unchanged and need their own full SQL input audit.

Validation: 31 actual Go SQLite cases plus six requests through Java JWT/API-key authentication; 277 relevant SQLite regression tests passed. Independent PostgreSQL uses all 115 Go schema migrations and a pool of one, exporting the actual Go corpus again and passing the same 37 comparisons. These compare complete ordered DTO/error responses, unchanged business tables, absence of queued tasks, and role-denial audit projections. Initial failures and exact source/report evidence are retained in [the checkpoint](move-targets-checkpoint-2026-10-16.json).

The packaged candidate passed discovery followed by real reuse/reparse moves in both `single` and `go` Java SQL-worker layouts. Each run checks physical sqlite-vec/FTS, original files, quota, Redis progress and move audit records. The `go` layout does not consume Go Asynq jobs. Full frontend UI interaction, every malformed legacy configuration, concurrent source mutation/list-query failures, all external stores and complete cancellation/restart/cutover remain unverified. The route remains `in_progress`, and the complete migration goal remains open.

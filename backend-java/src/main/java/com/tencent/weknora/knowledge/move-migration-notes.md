# Knowledge move migration

The next increment adds `KnowledgeMoveExecution`, the per-document state machine for both reuse and reparse. It is not yet a Spring bean or a public worker. Its required effects boundary still needs native engine, graph, image/file, Wiki and retained task-queue adapters before runtime admission can be connected; the HTTP/task coverage counts do not change.

The executor claims the source document in its own CAS checkpoint, then relocates indices, removes the source graph, moves all active chunks while clearing their tags, clears document tag relations, and finally checkpoints target ownership. Reparse cleans resources with a copy whose storage size is zero, so only the target checkpoint deducts quota; cleanup failures retain earlier effects for retry. A matching destination marker skips source cleanup and retries admission. Downstream tasks use the deterministic `move-reparse:<move task>:<document>` ID, seven-day retention, the Go queue/retry/timeout settings and target processing configuration. Duplicate/conflict admission still proceeds to acknowledgement. Acknowledgement reloads the current destination row and preserves a parser's status, metadata, summary and subtask count. Final-failure bookkeeping changes only a matching source `moving/processing` or target `reparse_pending/pending` row.

Production Go execution is exported with an isolated test overlay by `scripts/export-move-execution-oracle.py`. The 64 scenarios execute `moveOneKnowledge` and `markMoveItemFailed` with real SQL repositories. Java compares every stage's complete selected document/chunk/tag-relation state, quota, exact errors and ordered external calls, including the final-failure checkpoint and a second invocation. The scenarios cover both modes, every retained chunk type, independent chunk/tag/checkpoint failures, cleanup errors, quota rollback, pending/failed/done retries, queue conflict/duplicate, task payloads/options, parser/ack races and Wiki boundary failures. Go and Java independently pass 64 cases on SQLite and another 64 on PostgreSQL with all 115 versioned migrations and pool size one; the SQLite foundation/execution regression has 316 passing cases. The first Go fixture attempted an unavailable Asynq option accessor; it now reads the actual embedded option values using reflection. The first Java pass exposed a missing-document error-text difference and snapshot representation issues, all corrected before the passing runs.

External engine/model, graph, queue, Wiki lookup/pending failures and image-read failures are controlled in these scenarios. They do not prove physical vector relocation, extracted-image deletion, complete Wiki reconciliation, seven-day SQL/Asynq retention interoperability, public permissions/progress, or worker lifecycle. Dynamic SQL timestamps are excluded from the execution state projection; stored checkpoint timestamp semantics have separate foundation tests. Full tracing injection and runtime language resolution still need the native worker context. Run `python3 backend-java/scripts/postgres-move-execution-parity.py` for independent PostgreSQL execution, or select `KnowledgeMoveExecutionGoParityTest` with the SQLite native extension for the saved Go corpus.

This increment implements the shared move preflight and durable checkpoint layer. It does **not** register either public move route or a `knowledge:move` handler. The complete Go-to-Java migration remains in progress. Public admission, Redis progress, execution of both modes and the remaining lifecycle work must be connected and verified before those entries change status.

`KnowledgeMoveCompatibility` follows production `access.ValidateKBTransferCompatibility`: distinct KB IDs, identical type and embedding model (also for reparse), reuse only within the same vector-store binding, and the same concrete storage backend or legacy/default provider. Empty vector bindings mean environment fallback; whitespace is significant there. Concrete storage IDs are trimmed and take precedence over provider names. Provider priority preserves `__pending_env__` and legacy behavior.

`KnowledgeTransferMetadata` decodes the complete production `knowledgeTransferState` without replacing the existing, intentionally narrower `RejectMovingKnowledge` decoder. Outer keys are exact `map[string]RawMessage` keys; the last duplicate wins. Typed inner fields retain Go duplicate/null/folded-name handling and errors. Unrelated raw JSON retains number spelling and precision, object order, escaped strings and unknown fields. Setting the checkpoint sorts outer keys by UTF-8 order and applies Go HTML escaping.

`KnowledgeTransferRepository.plan` is read-only. It validates the pair and the entire ordered, deduplicated selection before returning any item. Blank IDs are rejected without trimming nonblank IDs. It checks the document's tenant/KB/status and persisted task/mode/source/target/phase, all chunk types, their parents and KB-scoped tags, manual content or retained source files, embedding model and index-move support. Matching `moving` retries can contain chunks already moved to the target. `done` and `reparse_pending` markers are accepted only on the target row. Engine validation occurs once and only for reuse with an embedding model. Go's tag model has no soft-delete field, so a physical `deleted_at` column is not added to the tag lookup predicate.

`checkpoint` updates only the transfer-owned columns, guarded by ID, tenant, previous KB/status/updated_at and the active-row condition. A concurrent title, custom metadata, file-path or subtask-count change is retained. Document and clamped tenant quota delta commit together; a missing tenant or quota SQL failure rolls back the document update. The returned timestamp is read from the database so a subsequent checkpoint still matches after storage precision changes. Each checkpoint remains a separate transaction.

SQLite CAS must also reproduce go-sqlite3's DATETIME decoding and binding. Go formats the previously read time as `2006-01-02 15:04:05.999999999-07:00` in its retained offset, and writes the new timestamp in UTC at microsecond precision. Consequently, an ISO `T`/`Z`, date-only, timezone-free or NULL persisted value can be readable yet fail the CAS. Java preserves these conflict results; canonical nanosecond and non-UTC-offset values can proceed. PostgreSQL normalizes valid timestamps on storage, so it has its own independently executed Go oracle.

The export fixture uses an isolated Go test overlay to call the actual unexported service functions and the actual repository. No production Go file is edited. It compares 252 cases: 155 compatibility, 23 raw/typed metadata, 53 batch preflight and 21 SQL checkpoints. Preflight snapshots prove that Go and Java leave the tables unchanged. The engine capability callback is controlled; this is not a test of physical index relocation. PostgreSQL runs all 115 versioned migrations, real SQL triggers and a Hikari pool of one. JSONB and timestamp outcomes come from that actual PostgreSQL execution, rather than the SQLite corpus.

```sh
mvn -f backend-java/pom.xml \
  -Dweknora.build.directory=/tmp/weknora-java-move-plan-check \
  -Dweknora.sqlite.vec.extension=/tmp/weknora-sqlite-vec-native/vec0.dylib \
  -Dweknora.move.plan.fixture=/tmp/go-move-plan.json \
  -Dtest=KnowledgeMovePlanGoParityTest test
python3 backend-java/scripts/postgres-move-plan-parity.py
```

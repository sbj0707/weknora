# Native tenant member management

The four list/add/update/remove member endpoints use the original Go route permissions and path-tenant match. Viewer may list; Owner may mutate. Machine credentials require `manage_members` or full access and may never assign Owner. Both human and machine operations preserve the last active Owner. A tenant-row write lock and a fresh membership role check prevent concurrent self-demotions from removing every Owner (verified with two real SQLite transactions).

Add resolves an existing undeleted account by email, including an inactive account as in Go; an unknown account must register first. It does not implement invitations, alter the user's home tenant, or silently reactivate an existing suspended/invited membership. Lists include undeleted invited/suspended rows because the actual Go repository does, despite its comment referring to active members. Safe DTOs omit password hashes, internal model timestamps and empty avatars; dangling user profiles yield empty public fields.

Mutations commit before best-effort audit records. Removal separately clears a matching home tenant and last-active preference, then revokes all user sessions; cleanup/audit failure does not undo the membership removal, matching Go. PostgreSQL supports re-add after soft deletion through its partial unique index; Go's SQLite plain unique index still reports conflict, preserved and tested.

# 知识库残留数据恢复

本脚本适用于 PostgreSQL 中仍有软删除记录的知识库。默认只读检查，执行恢复必须显式传入 `--apply`。需要项目要求的 Go 版本，可以使用已有的 `DB_*`、`REDIS_*` 配置，无需安装额外 Python 包。

**它不是回收站，也不是完整备份恢复工具。** 物理删除的文件、图片、向量/关键词索引、知识图谱、Wiki 历史版本和数据库记录无法凭 ID 重建。如果数据库中连知识库记录都没有，脚本直接退出，不创建空知识库。

## 1. 检查

在项目根目录运行：

```bash
bash scripts/restore-knowledge-base.sh \
  --local \
  --kb-id ba4e4694-37af-49a8-b4c6-bc56e9064c73
```

`--local` 用于本机 `make dev-app` 环境：将容器地址 `postgres`、`redis` 转换为 `127.0.0.1`。默认依次读取 `.env`、存在时的 `.env.local`，进程环境变量优先。支持单行 `KEY=VALUE`、`export KEY=VALUE`、引号和注释；按字面读取，不执行 shell、不展开 `$变量`。配置包含变量表达式时，请通过进程环境变量提供展开后的值。端口仍使用实际配置，本项目 `.env.local` 使用数据库 `5434`、Redis `6381`。

远程/容器环境不要加 `--local`，并显式选择该实例配置：

```bash
bash scripts/restore-knowledge-base.sh \
  --env-file /path/to/server.env --overlay '' \
  --kb-id ba4e4694-37af-49a8-b4c6-bc56e9064c73
```

如果需要独立数据库连接串，通过环境变量 `RESTORE_DATABASE_URL` 提供（PostgreSQL URL）；Redis 必须指向同一个应用实例使用的队列和 DB。不要把密码直接写进命令行。脚本不会输出数据库连接串或配置凭证。

检查会报告数据库名、知识库名称/空间/删除时间、残留记录和拟恢复数量，并扫描所有 Asynq 队列中的 pending、scheduled、retry、archived、active 删除任务。索引/文件完整性显示为未验证，而不会假定索引仍存在。

## 2. 恢复残留记录

先停止所有连接此数据库的 Go/Java 应用和独立 worker（包括其他服务器上的副本）；保留 PostgreSQL 和 Redis。等待正常退出后心跳过期。对已杀死进程遗留的 active 任务，需等待 Asynq 在受控维护过程中将其恢复到 retry，再停止 worker 重试，不能直接伪造任务状态。

```bash
bash scripts/restore-knowledge-base.sh \
  --local \
  --kb-id ba4e4694-37af-49a8-b4c6-bc56e9064c73 \
  --apply --maintenance-confirmed
```

远程环境使用检查时相同的 `--env-file` / `--overlay` 参数。`--maintenance-confirmed` 是操作者对停机状态的声明；脚本还会拒绝存在 worker 心跳或 active 删除任务的环境。它不会替你停止服务。

执行过程：

1. 锁定目标知识库，验证所属空间仍存在。
2. 将目标数据库记录及相关删除任务保存到 `.local-data/recovery/<知识库ID>-<UTC时间>/`，目录权限 `0700`、文件权限 `0600`。可用 `--backup-dir` 修改目录。JSON 含原始内容和配置，需妥善保管；它是操作前记录快照，不是文件/外部存储的完整备份。
3. 仅移除目标空间、目标知识库的 `kb:delete` 任务，包括可再次重试的 archived 任务。如果发现其他相关文档/索引删除任务则退出，由操作者逐项处理，避免取消跨知识库批量任务。
4. 在一个数据库事务中恢复知识库，以及在此次知识库删除之后软删除的文档、chunk、Wiki 文件夹/页面/问题。此前单独删除的文档和其 chunk 保持删除状态；其他空间和知识库不受影响。
5. 按该空间所有有效知识库中的有效文档记录重新计算 `storage_used`，避免重复运行时叠加用量。该字段基于保留的文档 `storage_size`，不证明外部存储实际完整。

数据库错误会回滚数据库事务。Redis 与 PostgreSQL 无法组成同一个事务：删除任务可能已移除而数据库提交失败，操作前任务快照会保留用于排查。此时保持停机，检查快照和错误后再重试，不要盲目重新入队删除任务。

## 3. 恢复后验证

重启服务，打开知识库并检查每个文档的原始文件、chunk 和索引详情。需要重建索引时从仍存在的原始文件重新解析；如果原始文件已经删除，需要从你的原始文档、对象存储历史版本或备份取回后重新导入。不会自动安排解析任务，也不会修改原有解析/索引状态；原有“完成/ready”状态可能已经过时。

分享、外部数据源及同步任务不自动恢复，避免恢复旧授权或立即触发同步，需手动重新配置。Wiki 版本历史和已经清理的引用需要备份或重新生成。

## 数据库中没有该 ID

先确认连接的是删除发生时的数据库。若仍找不到，则在独立恢复环境导入删除前的数据库备份及文件备份，再核对该知识库与外部索引。不要直接用旧的全库备份覆盖当前数据库，以免丢失删除后产生的数据。没有备份但仍有原始文件时，应新建知识库重新导入。

截至本次排查，本机开发数据库 `WeKnora` 中没有 `ba4e4694-37af-49a8-b4c6-bc56e9064c73` 的知识库、文档或 chunk 记录；在这个数据库上运行脚本会退出，不会恢复出空壳。

## 验证脚本

```bash
go test ./scripts/restore-kb
```

集成测试额外使用 `RESTORE_TEST_DATABASE_URL` 指定专用测试 PostgreSQL（测试会创建独立临时 schema 并清理）；未设置时跳过。不要将此变量指向生产数据库。
